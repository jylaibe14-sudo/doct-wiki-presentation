dOCT Wiki → HTML 簡報：可追溯的 Graph

這是一個有明確輸入、知識中介層與輸出檢查的工作流程。第一輪將研究結論與生物活性解釋分開；每次新增論文後重新 ingest、檢索與驗證，避免簡報生成時遺失研究限制。

NODE 01來源取得／查證4 份使用者 PDF＋2 篇可追溯外部研究；整理原文位置
NODE 02Ingest Wikiraw JSON → 6 篇來源摘要、9 篇概念筆記與索引
NODE 03Query & 教學編排查 LIV／OCDS／存活；按入門→分析→案例排序
NODE 04前置引用檢查查來源 ID、連結、可追溯性及高風險主張
NODE 05Generate HTML由同一組 JSON 生成 19 頁簡報與可搜尋 Wiki 網站
NODE 06瀏覽器驗證桌機／手機、滑動、跳頁、互動訊號與小測驗；合格才發佈
↶ Loop A：來源摘要未標出限制、或發現 S03 的 IV 被誤標為 LIV → 回到來源整理／Ingest。
↶ Loop B：來源不存在、主張缺乏證據、或誤稱「高 LIV 就是活細胞」→ 回到 Query／教學撰寫；通過檢查才能生成。
↶ Loop C：翻頁失效、SVG 顯示不良、手機溢位 → 回到 HTML／CSS 節點修正，再次測試。

為什麼要把檢查往前移？

若等投影片全部完成才發現「LIV＝細胞存活率」，會把錯誤複製到教學文字、圖示、問答與 Wiki。為減少返工，NODE 01 就先註明 IV 和 LIV 的定義差異；NODE 04 再查引用完整性與容易錯置的推論。

Node 06 是顯示與互動檢查，不代替光學數據或生物學驗證。

技術上真正有執行什麼？

已執行：Node.js 原始資料建構、摘要 Wiki ingest、關鍵字查詢、原始與投影片引用檢查、HTML 生成、故障注入、Chromium 瀏覽器測試。

沒有假稱：自動下載論文全文、向量資料庫檢索、LLM API 每一步自主循環或對 6 篇論文進行形式化事實正確性證明。這是一條可追溯、可重現的半自動工作流程。

反思：容易出錯的節點

哪一個節點最容易錯？

Node 03：將文獻內容轉成教學文字。因為會把研究中條件限定的「相關性」誤寫成「因果／絕對判定」；例如把 LIV 直接當成活細胞標記，或把 S03 的 IV 誤寫成 dB² LIV。

Graph 怎麼調整？

把研究限制與指標定義檢查往前移到 Node 01–02，並在 Node 04 加入來源 ID 與高風險說法的機械檢查。Node 06 增加手機排版與互動控制測試；出現錯誤即退回相應節點修正。

反思區分「實際故障注入」與真實測試結果：S99／錯誤主張是刻意加入的測試，不代表正式簡報含有這些錯誤；瀏覽器測試結果以 logs/browser-check.json 為準。
